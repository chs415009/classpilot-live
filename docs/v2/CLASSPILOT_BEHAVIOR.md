## 1. What ClassPilot Live does

ClassPilot Live runs a full class session when the professor is unavailable.

- The professor uploads raw course materials (slides and reference documents).
- The system turns them into a lecture: a spoken script for every slide, a set of
  polls placed at natural break points, and an explanation for every wrong poll option.
- In class, the web page shows the original slides while text-to-speech (TTS) reads the
  script. Polls appear at the planned points. Students can ask private questions at any
  time and get grounded answers on their phones.
- After class, the professor gets one report that covers everything that happened.

### The professor does only two things

1. Upload materials (one step: upload and preprocessing run together).
2. Read the post-class report.

There is **no review step in between**. Nothing generated by the system is approved by a
person before class. Automatic quality checks replace human review (see section 6).

### What changed from v1

| Topic | v1 | v2 |
|---|---|---|
| Professor role | Prepares content, approves branches, gives protected list | Uploads materials, reads report |
| Lecture | Professor-provided | Slides + AI-generated script read by TTS |
| Polls | Professor-provided | AI-generated, placement chosen by the LLM |
| Wrong answers | Lookup of pre-approved remediation branch | Pre-generated explanation per wrong option, read by TTS while the slide it names is shown |
| Correct answer | — | Revealed only; no explanation |
| Student questions | Analyst → Responder → Guardian | Same three agents, now built with DSPy |
| Protected assignment check | Rule against a professor list | Removed (future work) |
| Live LLM use | Poll path rules only + Q&A | Q&A only |

## 4. Prep phase (before class)

### 4.1 Inputs

| Material | Accepted formats | Notes |
|---|---|---|
| Slides | PPTX or PDF | PPTX also gives speaker notes. PDF has no notes. |
| Reference documents | PDF, DOCX | Books, readings, other course documents |

Test materials for development: slides from earlier courses, plus a reference document
generated separately with AI. The AI-generated reference is **synthetic test material**
and is labeled as such.

### 4.2 Flow from the professor's point of view

1. The professor creates a lesson and uploads the files.
2. Preprocessing starts right away. The page shows progress step by step
   (for example "parsing slides 12/40").
3. When it finishes, the lesson is ready to run. There is no preview or approval screen.

Uploading the same file again does not re-process it; the earlier result is reused,
also when the file is uploaded to a different lesson. If only a generation parameter
changes (for example `poll_count`), the content is generated again from the stored
parse result.

### 4.3 What the system produces

| Output | Description |
|---|---|
| Slide images | One image per slide, used for playback |
| Knowledge chunks | Text pieces from slides and references, each with its source file and page. Used to ground answers. |
| Lesson segments | The lesson split into topic segments, each with one learning objective (the objective id is the segment id) |
| Per-slide script | Plain-text spoken script for each slide, written for TTS (no raw code or formulas read out literally) |
| Polls | Question, four options, correct option, and the segment after which the poll appears |
| Misconceptions | For every wrong option of a poll: the misconception that option shows |
| Explanations | For every misconception: one explanation, read by TTS, with the slide to show while it is read and the chunks it cites. There is no explanation for the correct answer. |

### 4.4 Poll placement

- The number of polls is a parameter (default **5**).
- The LLM chooses where each poll goes, at the end of a topic segment.
- At most one poll per segment. If there are fewer usable segment ends than
  `poll_count`, the lesson has fewer polls. A poll after the last slide is allowed.
  There is no other minimum gap.
- Placement is fixed in the manifest before class. Nothing about order or timing is
  decided live.

## 5. Live phase (in class)

### 5.1 Lecture playback

1. The front end shows the current slide image.
2. TTS reads that slide's script.
3. When reading ends, the front end calls the next-page API and moves to the next slide.
4. If a poll is placed after this slide, the poll starts before moving on.

### 5.2 Poll flow

1. TTS pauses. The poll appears on students' phones.
2. Students answer within the answer time (parameter, default **60 seconds**).
3. When time is up, a **rule** (code, not the LLM) checks the result:
   - at least `min_responses` answers (default **5**), and
   - the most chosen wrong option has at least `wrong_ratio_threshold` of the answers
     (default **0.60**).
4. If the rule triggers and that wrong option has an explanation: TTS reads the
   pre-generated explanation, and the front end shows the slide named in that
   explanation (`show_slide`) while it is read. If the option has no explanation (its
   explanation failed the checks before class), the correct option is only revealed.
5. In all cases: the correct option is revealed (no explanation for it), and the
   lecture returns to where it stopped.

Each poll is asked once and triggers an explanation at most once. There is no re-poll
and no remediation deck.

The live backend sends the poll result to an HTTP endpoint of the agent service, which
runs the rule as a plain function. **[team]**

No LLM is called during a poll. All explanations were generated and checked before class.
A student who is still confused can use the normal question flow (5.3).

### 5.3 Student questions

Students can type a question at any time.

- The answer appears **only on that student's phone**. The lecture is not interrupted and
  the class does not hear it.
- This is the **only place the system calls an LLM during class**.
- The live backend sends each question to an HTTP endpoint of the agent service.
  **[team]**

Flow:

```
question -> Question Analyst -> retrieval (Cortex Search) -> Grounded Responder
         -> Guardian -> final validator (rule) -> answer or escalate
```

| Step | Type | What it does |
|---|---|---|
| Question Analyst | LLM | Classifies the question as in scope, out of scope, or assignment-like; links it to a learning objective |
| Retrieval | Search | Finds the most relevant knowledge chunks |
| Grounded Responder | LLM | Answers only from the retrieved chunks, cites chunk ids, gives a confidence |
| Guardian | LLM + rule | Lists each claim in the answer with the chunk that supports it; a rule fails the answer if any claim is unsupported |
| Final validator | Rule | Makes the final decision: answer or escalate |

**Answer:** the student sees the answer and which source pages it came from.

**Escalate:** the student sees a message that the question was saved for the professor.
Escalated questions appear in the post-class report. Reasons: out of scope,
assignment-like, low confidence, unsupported claims, or an LLM error / timeout.

Expected wait: a few seconds (v1 measured roughly 4–8 seconds for answered questions).
The phone shows a waiting state.

## 6. Quality control without human review

Because no person reviews content before class, every generated item is checked
automatically.

### 6.1 Before class (generated content)

1. Each script, poll, and explanation cites the chunk ids it is based on. The Guardian
   checks it against the chunks the generator was given, the cited ones first (Stage 9:
   true content the generator forgot to cite is not a failure). When the Guardian
   cannot tie a sentence to a chunk but code finds nearly all of its words in one
   given chunk, code passes that sentence:
   - script: every factual claim must be supported; transitions ("Let's move on to…")
     are not claims, and up to two content-free motivation sentences are allowed;
   - script and explanation: the writer may add its own short example, analogy, or
     rewording when it fits an idea the cited chunks state, and the Guardian names that
     idea's chunk (user decision, Stage 9: materials do not have an example for every
     idea). New facts are never allowed;
   - poll: the question and the correct option must be supported, and each wrong option
     must be shown wrong by the cited chunks;
   - explanation: every claim must be supported.
2. If it fails, the generator retries up to `prep_max_retries` times (**2**; 1 until
   Stage 9, raised because the prep Guardian's verdicts vary between calls), and each
   retry receives the Guardian's feedback (which claims were unsupported and why).
3. If the retries also fail, the system uses a safe fallback:
   - script: the slide's own text, cleaned for TTS (no code or symbols read
     literally). If the slide has no text, the vision description of the slide. If
     there is none, a fixed sentence asking students to look at the slide.
   - poll: if the poll fails, it is dropped and the next segment end is tried.
   - explanation: if a wrong option's explanation fails, the poll is kept and that
     option has no explanation; if it triggers in class, the correct option is only
     revealed (user decision, Stage 9: in Stage 7 this rule dropped every poll).
4. Every retry and fallback is recorded in the manifest (a status per item; the
   report counts them) and shown in the post-class report. Prep runs are not written to
   the analytics data model.

There is no separate report after preprocessing. Prep quality results appear only in the
post-class report.

### 6.2 During class (student answers)

- An answer is shown only if the Guardian and the final validator pass it.
- There is no retry during class (to keep the wait short). Anything that fails is
  escalated.

### 6.3 Fixed design rules

- Thresholds and final decisions are always code, never the LLM.
- Any LLM timeout or error leads to a safe outcome (fallback before class, escalate in
  class). The system never hangs.
- Every live decision writes trace records: the run, each node, each LLM call, each
  retrieved chunk, each Guardian claim, and the poll evidence. These traces are the only
  source of the team's analytics model. **[team]** (field names with Yaksha)
- Every live decision is also stored with its text (question, answer, sources) in the
  agent's decision log, which the report reads.

## 7. Post-class report

One report for the professor, produced after the session. The live backend calls the
report endpoint when the session ends; a CLI command does the same. The report is an
HTML page. Every number and list is computed by code; no LLM writes any part of the
report. Question and answer text comes from the agent's decision log. Contents:

- Attendance: connected students and how many took part in polls.
- Poll results: answer distribution and correct rate per poll; which polls triggered an
  explanation.
- Student questions: each question, the answer given with its sources, or the
  escalation reason.
- Escalated questions grouped for the professor to follow up.
- Content quality: which generated items needed a retry or used a fallback.
- System notes: LLM errors or timeouts, if any.

Every AI-written item in the report shows its sources, so the professor can audit the
session after the fact.

## 8. Parameters

| Parameter | Default | Where used |
|---|---|---|
| `poll_count` | 5 | Prep: maximum number of polls (at most one per segment) |
| `poll_answer_seconds` | 60 | Live: poll time limit |
| `min_responses` | 5 | Live: poll rule |
| `wrong_ratio_threshold` | 0.60 | Live: poll rule |
| `confidence_threshold` | 0.70 | Live: Q&A validator |
| `llm.timeout_seconds` | 10 | All LLM calls |
| `prep_max_retries` | 2 | Prep: Guardian retries |

## 9. Out of scope / future work

- Professor review or approval before class.
- Protected assignment check against a professor-provided list.
- Spread-out wrong answers (for example 40% / 40% on two wrong options does not trigger).
- Noticing when many students ask similar questions.
- Live-generated explanations.
- Explanations for the correct answer.
- Re-polling after an explanation; more than one explanation per poll.
- An LLM-written summary in the report.
- Reading answers to the whole class.
- Orchestrating prep through Airflow.

---

## 10. Known limitations

- Content is AI-generated and not reviewed before class; quality depends on the
  automatic checks.
- Grounding means "supported by the uploaded materials", not "true". Errors in the
  materials pass the checks.
- Diagrams are understood through an LLM description, which can be imperfect. Only
  pages that look like they contain images get one; a page the image check misses is
  understood from its text alone.
- LLM calls currently use cross-region inference. A later move to a Snowflake account
  in a region where the models run natively is possible, so account-specific settings
  are configuration, not code.
- Development uses synthetic reference material and a small evaluation set; results are
  exploratory.
